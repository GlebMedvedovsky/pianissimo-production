# Content package 1.0.0

[Current implementation and operating instructions](../README.md). This overview originated in stage 01; the current schema in `content.ts` and the 04A status in the main README take precedence.

`content.ts` is the runtime Zod schema and the source of TypeScript types. `manifest.schema.json` is generated by `npm run content:validate` for the existing PHP exporter. JSON data is the contract; neither Node nor Zod is required on the public web host.

The package has `schemaVersion`, `mode`, `sources`, `assets`, `projects`, `tracks` and `site`. Unknown schema versions fail. IDs/slugs are stable lower-case ASCII keys, never array positions. Text is plain text and rendered with framework escaping. External links must use HTTP(S), derivative paths must be relative paths under `media/`; do not put original private URLs or absolute filesystem paths in a public package.

Projects carry independent direction memberships and ordering. A membership does not copy a project or its tracks. Project→track joins own soundtrack order; the catalog reads the same IDs. Music categories, directing roles, genres and emotions are enumerated. Confirmed game soundtracks use the Games project category. No classification is inferred merely from a filename.

`published` means selected for this local prototype, not a claim of final legal/artistic approval. `draft` is excluded at the build-time boundary. `needs-confirmation` is shown only where explicitly allowed (the CV `tba` row), with an English label. `test` is rejected in an ordinary manifest. Media additionally carries approved/temporary/test state. This stage uses source-backed text and temporary working media.

`public-content.ts` filters projects/tracks/CV and referenced assets before serialization. The original source registry and provenance locations are removed from browser JSON. Client modules read that escaped JSON, never import the original manifest. Normal output isolation is checked after build. Files in public must be selected derivatives only: never use it as a draft/original storage folder.

`validateManifest` checks shape, duplicate IDs/slugs, asset types/references, source and track references, categories, optional values, duration/peaks and protocols. The CLI additionally checks derivative files. Release validation additionally requires mode=release, approved assets, published records, actual audio, confirmed legal content, email and production domain. It currently fails intentionally.

Future exporter: validate → export a complete versioned package → build in an isolated release directory on an external runner → verify output → stage → atomic activation. A failed build must never overwrite the active release. Draft preview packages and published releases have separate lifecycles. Export missing media as explicit null, not a nonexistent URL. Host paths, credentials and deployment policy remain to be established for this project.

04A adds backward-compatible optional fields to 1.0.0: `tracks[].libraryVisible` opts an otherwise projectless published track into the library; `projects[].presentationStatus: placeholder` labels a temporary cover; `site.cv[].linkText` limits an anchor to the confirmed name within a full text entry. Project and standalone tracks are deduplicated by ID. CMS-only draft notes, pending soundtrack order and legal review text are not part of the public contract. Both validators reject video on Letterboxd. Project categories include the supported Games classification; current enums, not the original PDF list, govern validation.
